# Post Investigation Outcome

Consume ticket_assessment and investigation_report from upstream stages. Missing or mismatched upstream output is an execution error, not a reason to invent questions or post. Preserve the investigation_report in the final output.

1. Re-read the input issue and all comment pages through Jira API v2, even if an earlier stage already read them. Verify the returned issue key. If assessment previously failed but these reads now succeed, report that investigation was blocked by the earlier read failure, not that the ticket was incomplete. If current reads fail or history is incomplete, return integration_error without posting.
2. Prepare one final Jira comment for every completed investigation, including diagnosed, needs_information, and escalate outcomes. A successful diagnosis, no remaining developer questions, or a resolved/closed issue is not a reason to skip the update. Keep closed tickets closed: post an informational summary, acknowledge the current status, and omit requests for action.
3. Summarize the investigated scope, outcome and confidence, key evidence with source references, recommended next steps with their owner/approval requirements, and verification checks. Clearly distinguish observed facts from hypotheses and recommended remediation from executed actions. State that this workflow performed no remediation. Redact secrets and sensitive data; do not paste raw logs or the full report JSON. If evidence is insufficient, say so rather than inventing a cause or a fix. Report operator/tool limitations separately with the appropriate operator follow-up.
4. For needs_information, include up to five highest-priority new blocking developer questions with stable field identifiers, reasons, and example answer formats. Remove questions answered by current fields, replies, or collected evidence. Compare prior asks semantically, including legacy [frontdoor-clarification:v1] comments. Do not re-ask outstanding questions or repeat the unanswered subset after a partial reply. Still post this run's outcome: briefly reference the earlier clarification comment when waiting on those answers, without repeating the questions. A diagnosed report needs no developer questionnaire.
5. Immediately before writing, re-read the issue and comments again and reconcile once. If new answers or changed scope invalidate the report, label findings as from the earlier ticket context, suppress stale questions/recommendations, and post that another investigation is needed; set ready_to_reinvestigate true. If the issue keeps changing, post a limited status update noting that findings need revalidation, with no stale action requests. Do not claim a rerun has been scheduled. Failed reads still produce integration_error rather than an unsafe write.
6. Include [frontdoor-investigation:v1] in every final comment. For retry deduplication, use an execution_id supplied by the caller (the same ID for retries, a new ID for a distinct investigation), or the platform's stable workflow execution ID if exposed. Never derive it from ticket text. Include it as [frontdoor-execution:<id>] only if it is 1-128 ASCII letters, digits, dots, underscores, or hyphens; otherwise treat it as unavailable. Suppress a POST only when an automation-authored final comment for this ticket and that same execution ID is confirmed; return already_posted with its ID. A similar outcome from a different execution must not suppress this run's update. Without a stable ID, do not invent one or infer same-run identity from matching text; cross-invocation retry deduplication is not guaranteed.
7. Use POST /rest/api/2/issue/{ticket_key}/comment with a string body. Make at most one POST attempt per execution; combine findings, limitations, and any questions into that single comment. Only return posted after receiving a comment ID or confirming the new automation-authored comment through a subsequent read. On timeout or uncertain write outcome, re-read once (paginate as needed) and match the execution marker and submitted body against comments absent from the pre-write snapshot. Without an execution ID, require an unambiguous new comment matching the submitted body and automation author. If unconfirmed, return delivery_unknown without retrying POST. On permission or API-version failure return integration_error. Preserve the prepared redacted comment in final output for operator follow-up when delivery fails.

Return JSON with investigation_report unchanged and clarification_result containing:

- ticket_key; status: posted, already_posted, delivery_unknown, or integration_error (delivery status, not diagnostic outcome).
- comment_id: null unless confirmed; comment_body: the redacted prepared/submitted comment, or null if preparation was unsafe.
- execution_id: the validated stable ID or null; comment_type: investigation_summary, information_request, operator_blocker, or status_update.
- questions: only the new structured developer questions included in the comment; ready_to_reinvestigate: boolean.
- reason and operator_blockers.

Keep the legacy clarification_result key for callers, but do not return not_needed, already_requested, or ready_to_reinvestigate as delivery statuses. A need to reinvestigate is represented by the boolean alongside the actual comment delivery result. This stage does not wait for replies or schedule another execution. Jira failures or a workflow failure before this stage can prevent delivery; never claim every invocation is guaranteed to post.
